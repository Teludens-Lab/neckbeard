# Output patterns

Apply references/delivery-formats.md: complete tutorials use MD, HTML, PDF, MP4 and MP3; written guides use MD, HTML and PDF unless narrowed by the user. Adapt names and locations to the repository. These are patterns, not mandatory files. Avoid duplicate documentation trees.

## Orientation

Explain purpose, audience, essential terminology, access, and the first useful action. Link to the correct path. Use a compact system diagram only when it clarifies relationships the learner needs.

## Learning path

| Task | Prerequisites | Outcome | Practice/check | Guide |
|---|---|---|---|---|

Keep each row actionable. Do not promise unimplemented workflows.

## Task tutorial

# [Accomplish a specific goal]

Audience and environment/version assumptions.

**Outcome:** Observable result.

**Before you begin:** Required access, inputs, prior tasks, and safe environment.

1. Perform an exact action using verified labels or commands.
   Explain a consequential choice if needed.
   State the expected visible result at meaningful checkpoints.
2. Continue to the complete outcome.

**Check your result:** Concrete evidence of success.

**If something goes wrong:** Symptom → likely cause → supported recovery. Distinguish confirmed causes from hypotheses.

**Try it yourself:** A different realistic task with success criteria, if appropriate.

**Next:** Relevant follow-on task or reference.

## Technical explanation

Answer a learner's specific conceptual question. Describe behavior, why it matters, relevant boundaries, and a concrete example. Separate current implementation from design intent. Use architecture details in proportion to audience needs.

## Reference

Use exact tables for permissions, fields, settings, commands, statuses, or errors. Include defaults, constraints, and version caveats only when established. Link to task guidance rather than embedding tutorials in every reference row.

## Contextual help

| Location/trigger | User's question | Proposed copy | Supported next action | Source/evidence |
|---|---|---|---|---|

Mark all copy as proposed unless already implemented. Fit the available interface space when known. Give errors an actionable next step only when supported.

## Verification and maintenance record

Include scope, inspected revision, audience assumptions, evidence ledger, executed checks, blockers, and document-to-source mapping. Keep this separate from the learner's primary path. List product issues separately from documentation gaps.

## Small default package

For a broad first pass, prefer a concise start page, one role path, one complete first-task tutorial, relevant troubleshooting, and a verification record. Expand only when requested or when another audience/task is essential to the stated goal.
