# Organizational governance and localization

## Profile
During step 1 resolve `--profile`, then `<project>/.neckbeard/org-profile.yaml`, then `<project>/org-profile.yaml`. The bundled profile is a restrictive template, not an organization's approval. Copy it into the project and configure house style, glossary, documentation platform, required templates, approved tools, classifications, and mandatory reviewers. Do not invent organizational reviewers or silently approve tools. With no project profile, produce drafts only and keep all external media processing blocked.

Run `python scripts/governance.py profile --profile PATH` before production. It validates profile structure; it does not verify a reviewer's identity. Scripts accept JSON-compatible YAML with the standard library; install `requirements.txt` for full YAML syntax.

## Artifact contract
Every artifact must have owner, primary source revision, evidence state, reviewer, review-by date, stable document ID, and locale. Use `references/governed-document.md`; binaries use a metadata companion. Publish the machine record beside outputs as `governance.json`; use `scripts/governance.py export` to emit `documents.csv`, `evidence.csv`, `mapping.csv`, `media-gate.csv`, and `audit.md`. Preserve exact per-repository commits in each document's `sources`. Use repository IDs rooted at the actual Git checkout, not ambiguous local folder names. Paths must be relative to that Git root, even when the task is scoped to a subdirectory. Before recording HEAD, check whether each inspected file is tracked and unchanged at that commit. For untracked or modified inputs record `working-tree:<base-commit>:<snapshot-hash>` with per-file SHA256 and base_revision; never attribute changed bytes to HEAD. Such snapshots stay draft and require a committed revision before release. Never place secrets or raw personal data in the record.

List the applied required templates in each document record’s `templates` field. Validation with a profile checks that all mandatory templates are represented.

Use `references/governance-example.json` as the data shape, not as real evidence. Evidence states: runtime-verified, source-supported, documentation-only, unverified. Every document cites evidence IDs; every source dependency has a matching ledger entry. Each ledger entry records source repository, revision, path, claim, method, result, and limitations. A runtime-verified document requires passed runtime evidence, not code inspection alone. Accountable decisions live in `reviews`. The owner may also be the sole reviewer when the organization policy permits it; no independent reviewer is inherently required. Record explicit owner authorization as such, without describing it as an independent review or learner test.

`validate --record ... --profile ... --root ...` validates content, local files, source/evidence coherence, dates and locale/glossary consistency. `--release` additionally requires a nonempty document package, no linked failed evidence, and current approved decisions from every mandatory reviewer and the named reviewer. Every effective approval includes `artifact_sha256`, the lowercase SHA256 of the entire final artifact's bytes (including Markdown frontmatter), plus `source_revision` and the complete `sources` list. Finalize metadata before hashing. Binary and HTML artifacts hash the artifact itself; their companion metadata is checked separately. A changed artifact or legacy approval without a hash cannot pass release validation. Do not silently attach new hashes to old approvals.

The latest dated decision per reviewer applies; later list entries win ties on the same date. Keep superseded decisions as history and append an authorized renewal for changed bytes or dependencies. A review date cannot be in the future. `review_by` must be on or after that date, no more than `review_interval_days` later, and not already overdue; the deadline itself remains valid. These checks apply to every required approver, including a sole owner. They add no separate reviewer role or interactive approval command. Failed evidence may remain in a draft audit, but must be resolved before release; a source-supported guide may still explicitly describe runtime checks that were not run.

A prose audit is supplementary; machine records are authoritative for checks. Metadata can be forged; these checks do not authenticate reviewers or create a compliance certification. Existing schema-version-1 drafts remain readable; existing release approvals need an authorized hash-bound renewal before they can pass the stricter release checks.

## Continuous maintenance across repositories
`stale --record ... --repo product=/checkout --repo api=/other-checkout` compares each document's mapped source revision against that repository's current HEAD. Glob paths are repository-relative; include all dependencies that affect the workflow, including permissions, APIs, schemas, fixtures, and client behavior. A changed mapped path, overdue date, missing checkout, unresolved commit, or dirty checkout flags review. Output JSON and a nonzero exit code allow CI gating. Renames/deletions are considered. Unmapped behavior is not covered: report this limit and update mappings as new dependencies emerge.

Install `.github/workflows/neckbeard-maintenance.yml` into consuming projects and configure the record/profile paths. Check out every private dependency explicitly with approved read-only credentials and full history. Do not discover or fetch repositories from record-provided URLs. Missing multi-repository checkouts fail closed. Ordinary pull_request checks do not execute application code or tutorial commands. Do not use pull_request_target on untrusted code. CI flags stale material; an author verifies and revises it, refreshes dependency revisions and evidence, then obtains the required review.

## Data handling before media production
Inventory screenshots, demo datasets, narration, transcripts, captions, logs, and render inputs in `media_assets`; default unclassified inputs to the profile's restrictive default. Record explicit classification, contains_personal_data, sanitized, reviewer, reviewed status, and SHA256 of the reviewed file bytes. Sanitization is a human-verifiable claim, not automatic declassification. Use synthetic data; remove identifiers from pixels, hidden layers, filenames, metadata, logs, and spoken content. Classified inputs are offline-only; unknown classes or tools are denied.

Before any capture/voice/render invocation run `gate --profile ... --record ... --tool ID --operation voice --mode external|offline --root ASSET_ROOT --assets ID...`. Pass only the approved asset IDs. An exact approved tool must match operation, execution mode, classification, personal-data policy, and completed asset review. Store returned receipt in the evidence package. Re-run when inputs, tool, mode, or policy change. No gate result grants broader permission than the user's authorization. Offline mode denies external tools and makes no external calls; its networking must also be disabled by the actual execution environment. This script is a policy preflight, not a sandbox or an external-service interceptor. If tools cannot meet the policy, deliver a local script/storyboard rather than send inputs.

## Localization
Use the profile's shared glossary with stable term IDs, definitions, source language, approved translations, and do-not-translate flags. Keep exact UI labels, code, identifiers, placeholders and command syntax intact; explain labels in the target language without inventing localized UI. Author short independent segments and avoid text baked into images. Each translated artifact lists `translation_of` and its own locale, owner, reviewers, date, and source mappings. Reuse source task/shot IDs to link translations and captions. Any source change marks translations stale through the same mappings. Flag missing glossary translations for review; never present machine translation as professionally reviewed. Check locale-specific number/date formats, RTL rendering, text expansion, pronunciation, and caption timing where relevant.
